Análise Detalhada: Pipelines DeCS V1 e V2 vs. os 6 Pontos do Documento
Ponto 1 — system_instruction Dedicado
Status: ✅ Implementado — com um problema crítico escondido

Todas as chamadas usam o campo correto:

Local	Implementação
V1 /decs-ai/route.ts (extração de temas)	config: { systemInstruction: systemPrompt } via SDK
V1 validateDescriptorsWithGemini	system_instruction: { parts: [{ text: VALIDATION_PROMPT }] } via fetch
V2 indexer (runDeCSPipelineV2)	system_instruction: { parts: [{ text: indexerPrompt }] } via fetch
V2 selector (selectDescriptorsWithGemini)	system_instruction: { parts: [{ text: selectorPrompt }] } via fetch
Problema real: Tanto o prompt do decs_classifier quanto o do decs_indexer_v2 terminam com a linha [INSERIR QUESTÃO AQUI] dentro do system prompt, não no turno do usuário. O modelo recebe essa instrução como parte do "papel" e pode interpretá-la literalmente, criando confusão de papéis (system vs. user). É um artefato de quando os prompts eram usados via template — deve ser removido.

Ponto 2 — Temperatura e Top-P
Status: ✅ Temperatura bem calibrada — ⚠️ Top-P/Top-K não configurados

Agente	Temperatura configurada no código
V1 — extração de temas (route.ts)	0.1 ✅
V1 — validação Gemini	0 ✅
V2 — indexador	0.1 ✅
V2 — seletor	0.05 ✅
Os valores de temperatura estão corretos para tarefas técnicas de indexação. Entretanto, nenhuma chamada define topP ou topK explicitamente — fica nas mãos dos defaults da API, que para o modelo gemini-3-pro-preview (com thinking mode) podem ser bem altos.

Problema secundário: Os defaults em ai-agents-defaults.ts guardam temperature: 0.1 e model: 'gemini-2.5-flash' para todos os agentes DeCS, mas esses valores nunca são lidos em runtime — as chamadas à API constroem o body diretamente com valores hardcoded. O campo model da tabela de defaults está desconectado da execução real.

Ponto 3 — Gestão de Contexto (Chat vs. Prompt Único)
Status: ✅ V2 bem resolvido — ⚠️ V1 perde contexto na validação

V1 — fluxo de 3 etapas:

Gemini extrai temas → recebe só o questionText ✅
Busca DeCS por tema (sem LLM) ✅
validateDescriptorsWithGemini → recebe questionText + lista de candidatos com code/term/scope ✅
O contexto chega na etapa 3, porém sem o raciocínio da etapa 1. O modelo de validação não sabe por que aqueles temas foram escolhidos — só vê os candidatos já filtrados. Para uma questão com nuance clínica, isso reduz a precisão.

V2 — fluxo de 2 etapas com RAG:

Indexador recebe só questionText → retorna strings de temas ✅
Seletor recebe o objeto completo:
{
  "questao": "...",
  "temas_primarios": [{ "conceito_buscado": "...", "candidatos": [...] }],
  "temas_secundarios": [...]
}

A questão original + os conceitos identificados + os candidatos reais com scope_note e árvore hierárquica chegam juntos ao seletor. Esse é o fluxo ideal descrito no documento. ✅

Gap no V2: O indexador (etapa 1) recebe apenas o texto puro, sem nenhuma instrução de formato JSON explícito no contents. A questão vai direto como texto no turno do usuário, o que é correto, mas o raciocínio interno (o clinical_core, domain, etc.) não é capturado no output — o modelo joga fora esse raciocínio e retorna só os temas.

Ponto 4 — Extração de Dados e JSON Mode
Status: ❌ Não implementado — maior risco de falha silenciosa

Nenhuma chamada nos dois pipelines usa responseMimeType: "application/json" nem responseSchema. A extração é feita assim em todos os 4 pontos de chamada:

const cleaned = rawText.trim()
  .replace(/^```json\s*/i, '')
  .replace(/```\s*$/i, '')
  .trim();
const parsed = JSON.parse(cleaned);

Isso tem duas implicações diretas:

Qualquer prefácio textual ("Aqui está o resultado:...") antes do JSON quebra o parse.
O modelo não é forçado a respeitar o schema — pode retornar decs_primary quando o código espera primary, ou omitir campos. De fato, esse é o bug confirmado no scratchpad: o prompt do decs_indexer_v2 instrui o modelo a retornar decs_primary/decs_secondary com objetos {id, term, parents, children}, mas o pipeline espera {primary: string[], secondary: string[]}. O JSON mode com schema resolveria isso ao forçar o formato correto.
V1 ainda tem um fallback de regex como último recurso (rawText.match(/"([^"]+)"/g)), o que é frágil. V2 não tem fallback de extração — se o parse falhar, cai direto no themes = { primary: [], secondary: [] } e dispara o fallback de fragmentos de texto, que é ruim.

Ponto 5 — Few-Shot Prompting
Status: ❌ Não implementado em nenhum dos dois pipelines

Todos os prompts são zero-shot — por mais detalhados que sejam as instruções, não há nenhum exemplo concreto de entrada + saída esperada. O documento cita que 2-3 exemplos resolvem 80% dos problemas de precisão.

O gap é mais crítico no decs_indexer_v2, que precisa retornar um formato específico, e no decs_selector_v2, que precisa justificar a escolha de um candidato sobre outro. Um exemplo como:

Questão: "Paciente com febre, tosse e derrame pleural. Qual o diagnóstico?"
Conceito: "derrame pleural"
Candidatos: [D010996 Pleural Effusion, D010995 Pleuritis, ...]
→ Correto: D010996 (Pleural Effusion) — "febre + tosse + derrame" remete ao descritor específico, não à inflamação

...ensinaria o seletor a usar o campo scope para distinguir candidatos próximos.

Ponto 6 — Versão do Modelo
Status: ⚠️ Modelo Pro usado corretamente — mas há uma inconsistência arquitetural

No código de runtime, todas as chamadas usam gemini-3-pro-preview de forma hardcoded:

Arquivo	Modelo no código
app/api/questions/[id]/decs-ai/route.ts	'gemini-3-pro-preview'
lib/decs-pipeline.ts (validateDescriptorsWithGemini)	model = 'gemini-3-pro-preview' (default do parâmetro)
lib/decs-pipeline-v2.ts (indexer)	'gemini-3-pro-preview' hardcoded
lib/decs-pipeline-v2.ts (selector)	'gemini-3-pro-preview' hardcoded
O uso do modelo Pro para curadoria final é correto. Porém, os defaults em ai-agents-defaults.ts declaram model: 'gemini-2.5-flash' — esse campo nunca é lido nos pipelines DeCS, porque as chamadas constroem o body da API diretamente sem passar pelo orquestrador ai-agents.ts. Existe uma divergência entre o que está na configuração e o que executa de fato, o que pode causar confusão futura.
